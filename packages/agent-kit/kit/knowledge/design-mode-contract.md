# Design Mode Contract

Use this knowledge when generating screens, editing a selected visual target,
or fixing a screen that Design mode cannot inspect.

## Two Levels Of Support

sber-designer must open arbitrary connected projects. Old project screens do
not need to be Design-readable before the user can select something and ask the
agent to work on it.

`baseline-selection` support means:

- use the selected DOM element as context even when `loc` starts with
  `dom://`;
- preserve tag name, visible text, selector or DOM path, rect, component path
  and safe attributes;
- direct visual controls may be locked, but the selection is still useful for
  source search and narrow edits.

`Design-readable output` is stricter. New screens generated by
`ai-product-designer`, and substantial rewrites of legacy screens, must be
structured so future Design mode edits can use inspector capabilities and AST
patches instead of only DOM fallback.

## Generate Design-Readable Screens

Prefer:

- real React/TSX/JSX source;
- clear screen implementation files with thin Storybook wrappers;
- project components from Catalog and design-index before custom markup;
- design tokens and known component props before raw CSS;
- semantic sections, cards, forms, lists and toolbars that become useful
  Layers rows;
- plain text children or string props for editable copy;
- string/number/boolean literal props for first-pass controls;
- literal `className` strings when class editing should be deterministic;
- narrow `style={{ ... }}` objects only for MVP-safe style values;
- `data-sd-flow-id`, project-conventional `data-testid`, and `aria-label` for
  important controls.

Avoid:

- `dangerouslySetInnerHTML` or large raw HTML strings for editable UI;
- hiding the whole screen in factories or computed arrays;
- rewriting an entire screen to change one selected element;
- expression-heavy `className` on elements that Design mode should edit;
- editing shared component definitions unless the user explicitly asks for a
  component-level change.

## Capability-Aware Editing

When Design mode reports capabilities:

- `editable`: use the exact shared operation name.
- `assistant-only`: make a narrow source edit and explain why direct visual
  controls were not safe.
- `read-only`: do not bypass project policy or source ownership.
- `unmapped`: use selector/text/attributes/active screen context to locate the
  likely source, then make the touched output more Design-readable.

Shared visual operation names:

- `set-children-text`
- `set-prop`
- `remove-prop`
- `set-style`
- `remove-style`
- `set-class-token`

For inserts, swaps and layout restructuring, prefer a small assistant-planned
patch until a deterministic AST operation exists.

## Compatibility Levels

- `unknown`: no indexed screen record or source mapping is available yet.
- `baseline-selection`: selection can be sent to the agent, but direct visual
  controls may be locked or assistant-only.
- `design-readable`: source location, scope, capabilities, props, styles, and
  component metadata are available enough for deterministic edits.

Generated and repaired screens should move toward `design-readable`. Legacy
screens only need the baseline scenario to keep working: select an element,
send the agent a task, and let the agent resolve source through selection,
active screen, index, and file reads.

## Required Inspector Vocabulary

When a tool returns inspection data, preserve these fields in reasoning and
summaries:

- `projectSupport`
- `sourceScope`
- `capabilities`
- `diagnostics`
- `target.filePath`
- `target.loc`
- `target.sourceKind`

Do not translate this vocabulary into a private format inside agent output.
