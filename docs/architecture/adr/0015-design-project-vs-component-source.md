# ADR-0015: Проект = design-project; библиотека компонентов — опциональный подключаемый источник

- **Дата:** 2026-06-19
- **Статус:** Accepted (продуктовое решение 2026-06-19); реализация поэтапно — задача разработки 0300. Refines [ADR-0001](0001-live-dom-canvas.md); связан с [ADR-0004](0004-three-modes.md), [ADR-0008](0008-local-spawn-sandbox.md).
- **Контекст:** модель «что такое подключённый проект».

## Контекст

Сегодня «проект» в sber-designer — это рабочая копия ui-kit, и экраны пишутся
**внутрь того же репозитория** (`src/screens/**`, `src/stories/screens/**`,
`.sber-designer/runs/**`). Из-за этого:

1. Репозиторий публикуемой библиотеки засоряется черновыми макетами.
2. Слой описаний компонентов ([0083]) и история правок заперты в одной рабочей
   копии, хотя по смыслу они — переиспользуемый актив самой библиотеки.
3. Граница «kit ⟂ screen» уже существует, но лишь как **мягкое правило** внутри
   одного репо: агенту запрещено писать в исходники компонентов при правке
   экрана ([prompt-builder.ts:595](../../../services/api/src/prompt-builder.ts)).
4. Сценарий «без библиотеки вообще» (OpenDesign-режим: генерим HTML / свои
   базовые компоненты) не выражен как первоклассная модель.

Нужна модель, которая разделяет «где лежат макеты» и «где лежит библиотека», при
этом сохраняет live-DOM canvas ([ADR-0001](0001-live-dom-canvas.md)) и текущую
возможность эволюционировать kit в той же сессии.

## Решение

**Инвертируем роль «проекта».** Первичная единица — **design-project**
(создаётся в sber-designer; держит `.sber-designer/project.sdproj`, экраны, flow,
комментарии, историю ассистента, `runs/`). **Библиотека компонентов —
опциональный подключаемый источник**, а не сам проект.

Два режима по наличию внешнего репо:

- **A. Standalone** — внешнего репо нет. DS задаётся одним из: ничего → чистый
  HTML/примитивы (OpenDesign-режим); `design.md`
  ([design-md-spec.ts](../../../services/api/src/design-md-spec.ts)); или
  **сгенерированный дефолтный компонент-пак по одной кнопке** (поверх
  [scaffolder.ts](../../../services/api/src/scaffolder.ts) + `POST /api/scaffold`,
  которые уже умеют Vite+React+TS и init Storybook).
- **B. Connected** — внешний репозиторий компонентов подключён как **живая
  редактируемая рабочая копия**: индексируем + описываем ([0083]), используем как
  «кирпичики», и **пишем в него новые компоненты из sber-designer**. Внешний репо
  обновляется самостоятельно (свой git).

**Single-repo (kit = проект) остаётся частным случаем**, где design-project и
источник совпадают, — он не ломается.

### Почему так

- ✅ Совпадает с ментальной моделью Builder.io Fusion / OpenDesign («дизайн-проект
  ссылается на дизайн-систему»), ср. [0202].
- ✅ Библиотека перестаёт засоряться макетами; описания [0083] — её актив, общий
  для многих проектов.
- ✅ Эволюция kit идёт **отдельным PR в его репозиторий** — для review чище, не
  грязнее; смысл «эволюция в той же сессии» сохраняется за счёт живого линка.
- ✅ OpenDesign/empty-режим выражается естественно; быстрый старт собирается из
  **готовых** примитивов (scaffolder, design.md, design-indexer).
- ✅ Формализуем уже существующую мягкую границу «kit ⟂ screen».

### Почему живой линк, а не опубликованный пакет

Опубликованный пакет (`@sber/ui-kit@x`) не даёт писать компоненты в kit вживую
и требует publish-цикла — это убивает сценарий эволюции kit в сессии. Поэтому
дефолт — **managed live link** (Vite path-alias / workspace-линк на соседний
чекаут), который sber-designer прописывает сам при «Attach component repository».
Опубликованный пакет — возможная опция позже для «замороженных» kit.

## Последствия

**Требует repo-квалификации там, где сегодня один workspace:**

- **Резолвинг/sandbox:** dev-server design-project должен резолвить источник
  через линк ([session.ts](../../../services/sandbox/src/session.ts)); каталог
  компонентов может приходить из Storybook источника. Принцип «один active
  iframe для всех editor modes» ([ADR-0004](0004-three-modes.md)) сохраняется;
  bounded passive screen cache уточнён в [ADR-0018](0018-bounded-screen-preview-cache.md).
- **Write-scope агента:** мягкое правило → жёсткое, по репозиториям ([0030]).
- **Git/PR + handoff:** два git-root → два PR-потока (component-PR, screen-PR) и
  двойной handoff-таргет ([0013], [0053]) — самый дорогой кусок.
- **`data-sd-loc`:** путь в loc-атрибуте квалифицируется репозиторием
  ([ADR-0007](0007-fiber-source-detection.md)).
- **Реестр:** запись Projects Home ссылается на источник(и) (id + путь +
  отпечаток версии); detach-семантика [0012A] переносится на оба репо.

**Открытые вопросы** (происходят из задачи разработки 0300):
привязка версии источника, деградация без линка, число источников на проект,
монорепо-источник, содержимое дефолтного пака, миграция single-repo → split.

**Реализация — поэтапно** (priority high): Фаза 0 standalone-режим → Фаза 1
дефолтный пак → Фаза 2 connected live link → Фаза 3 repo-aware write-scope/loc →
Фаза 4 два PR-потока + двойной handoff.

## Альтернативы

- **Оставить только single-repo.** Отклонено: библиотека продолжает засоряться,
  описания не переиспользуются, OpenDesign-режим не выражен.
- **Линковать через опубликованный пакет.** Отклонено как дефолт (см. выше);
  оставлено опцией для замороженных kit.
- **Git submodule/subtree источника в design-project.** Отклонено: болезненный
  UX линковки и обновления по сравнению с managed alias/workspace.
