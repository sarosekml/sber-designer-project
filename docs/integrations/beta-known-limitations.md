# Известные ограничения закрытой беты

Этот документ — часть контракта серверной беты sber-designer. Ограничения
ниже не считаются изоляцией enterprise-уровня; выдавайте доступ только
доверенной команде и закрывайте регистрацию после онбординга.

## Владение и совместная работа

- Один серверный workspace и одна плитка проекта принадлежат одному
  пользователю. Общего редактируемого workspace для команды пока нет.
- Передача проекта выполняется через git remote: второй пользователь клонирует
  репозиторий в своё поддерево. Для просмотра можно использовать read-only
  share-ссылку.
- Один пользователь в двух вкладках работает по last-write-wins. Одновременное
  редактирование одного экрана не разрешает конфликты как collaborative editor.
- В одном проекте одновременно выполняется один agent run. Остальные клиенты
  видят busy-состояние и автора активного запуска.

## Исполнение кода и ресурсы

- Встроенная аутентификация не является sandbox security boundary. Агент,
  git-команды и `local` sandbox запускают код проекта от системного
  пользователя сервера. Это принятый риск Р-16: TLS обязателен, регистрация
  открывается только на окно онбординга, публичный стенд без доверенного
  контура не поддерживается.
- Sandbox использует local-spawn по умолчанию. Docker-driver остаётся
  экспериментальным и не превращает бету в multi-tenant платформу.
- Один живой Storybook обычно требует около 1–2 GB RAM. Число одновременных
  сессий на сервере ограничивает `SBER_DESIGNER_SANDBOX_MAX_SESSIONS`
  (server default 5; `0` отключает новые сессии). При заполнении лимита запуск
  получает HTTP 429. У обычного local profile лимита по умолчанию нет; его
  можно включить явным значением env.

## Local и enterprise auth-контуры

- Plain local сохраняет legacy CORS-контракт: API отражает любой
  browser Origin и принимает `x-sber-designer-user`. Поэтому local API на
  `localhost:3000` надо запускать только на доверенной машине и не открывать
  недоверенные сайты в том же browser profile во время работы: такой сайт
  потенциально может обращаться к файловым и исполняющим API. Целевое
  исправление — отдельный проверяемый local token/origin allowlist в
  enterprise/local-agent треке.
- OIDC/Keycloak не входит в password-бету. Текущий compatibility path оставляет
  WebSocket `/api/events` без проверяемого upgrade-token и позволяет socket
  subscribe/publish; не включайте OIDC deployment до закрытия WS-auth contract
  в security pass Этапа 12. Password server mode этот маршрут защищает сессией.

## Удаление и восстановление

- Удаление пользователя сначала переносит его данные в админ-корзину. Проекты
  с незакоммиченными изменениями, коммитами без remote или без remote вообще
  явно помечаются как «not pushed anywhere».
- Корзина не очищается автоматически: TTL и фонового purge нет. Только
  администратор вручную выполняет **Restore to user…** или подтверждённый
  **Purge**. Purge необратим.
- Проект с remote пользователь восстанавливает повторным clone. Проект без
  remote может вернуть только администратор из Trash. Экраны, описания и
  `.sber-designer/project.sdproj` должны храниться в самом репозитории;
  `.sber-designer/runs/` остаётся локальным run-evidence и игнорируется git.

## Модель хранения

- Реестр плиток, explicit uploaded thumbnails, `coverScreenId` pin и серверные
  пользовательские настройки файловые, в
  `~/.sber-designer/users/<userId>/`. Generated cover лежит в самом workspace:
  `.sber-designer/previews/cover.webp`/`.png` и переносится через git;
  `.sber-designer/previews/screens/` остаётся local-only. Workspace'ы
  ограничены `SBER_DESIGNER_PROJECTS_ROOT/<userId>/`; чужой project id
  возвращает 404.
- Старый общий `projects.json` импортируется только первому администратору с
  отметкой `legacy`. Разложить такие workspace'ы по владельцам нужно вручную
  по SSH.

## Модели и CLI

- Базовый server-managed провайдер задаёт администратор в
  `/etc/sber-designer/sber-designer.json`; его ключи остаются в серверном
  env-файле.
- Отдельный `bun run dev:server` и runtime-изоляция local/server готовы.
  Personal API connections из Settings и их зашифрованное account-scoped
  хранилище остаются незавершённой частью серверного сценария.
- Удалённый backend не видит CLI, установленные на ноутбуке пользователя. В
  server mode допустимы только отдельно установленные администратором
  **Server CLI agents**.
- Local mode сохраняет текущий путь: `bun run dev`, папки на диске
  пользователя, локальный provider config/env и CLI той же машины.
